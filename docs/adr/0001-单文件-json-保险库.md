# 保险库采用单文件 JSON 加密格式，不用 SQLite/SQLCipher

保险库是单个 JSON 文件，整体经 AES-256-GCM 加密后落盘，用临时文件 + fsync + rename 保证原子写入。这条路一开始就被 PRD §3.2 否决过（理由是「个人项目没必要重数据库负担」），§8.8 又自我推翻过一次（「几千条条目改用 rusqlite + SQLCipher」）。现在正式定死，且 §8.8 作废。

## 为什么不是 SQLCipher

1. **交叉编译成本**。SQLCipher 是 OpenSSL 的 C 绑定，要为 Android NDK、iOS、Windows、macOS、Linux 各建一套。Rust core 还要经 FFI 喂给 Flutter，这是整个项目最大的构建风险源，而它换来的东西是零。
2. **SQLite 解决的是不存在的问题**。条目约 110 字节，5000 条约 550 KB；解密不到 5 ms，5000 次 TOTP 计算约 10 ms，内存线性搜索约 1 ms。
3. **备份必须是字节拷贝**。恢复模型（见 ADR-0002）依赖「复制文件即可恢复」。SQLCipher 无法原子覆盖数据库，备份要走 SQLite Backup API 或 `VACUUM INTO`，而那个 API 的行为在各版本间并不一致。
4. **双层加密无收益**。SQLCipher 已有页级加密，再叠保险库密钥会让密钥派生参数重复校准，故障时无法判断是哪一层出错。

## 为什么不是 MessagePack

OTP 条目的每个字段本来就是文本（密钥是 Base32 文本，RFC 4648），MessagePack 的体积与速度优势接近于零。它唯一的关键劣势是决定性的：**救援能力**。用户存的密钥一旦全部锁死、备份文件损坏或需要跨大版本升级，JSON 能用任意语言写十行脚本抢救数据，MessagePack 必须依赖自家工具——而那个工具本身可能正是有 bug 的那个。

## 后果

- 备份 = 文件复制，无导出/导入转换层。
- 文件格式必须带 `schema_version`，且升级路径要保证老文件永远可被新版本读取。
- 若日后条目规模真的突破十万量级，这条决策会被重新审视，但那时应当先测量再推翻，不要预先引入数据库。
