# 保险库文件格式与版本迁移策略

保险库文件 = 明文头部 + AES-256-GCM 密文。头部携带 `schema_version`、nonce 与封套列表，并整体（含 magic）作为正文 GCM 的 AAD 被认证。盐与 `kdf_version` 由每个封套自带，封套密文以自身的盐与 `kdf_version` 为 AAD——重写任一封套都不影响另一封套的认证。明文头部只含密码学元数据；条目内容与条目数量全在密文内。

## 版本演进

`schema_version` 单调递增，v1→v2→v3 逐级迁移，每级是一个可单独测试的纯函数。迁移前自动生成 `.bak`，写入走临时文件 + rename，因此可中断而不损坏。自家加密备份导入走同一条迁移链——否则一份四个月前的备份会被新版本拒收，而用户根本不知道自己手里有唯一一份数据。

## 为什么不用隐式容错

`#[serde(default)]` 加可选字段看着能省掉全部迁移代码，实际会在三种情况下静默丢数据：字段重命名（老字段被忽略、新字段取默认值）、新增必填字段（反序列化后是空的）、嵌套结构改变。而 2FA 的失败模式没有「降级可用」这一档——一个服务商名丢失用户在登录页就看不到账号，一个密钥丢失用户就永久失去该账号访问权。用户甚至不会收到错误提示，只会看到「验证码不对」。显式迁移链让每一次格式变更都必须显式处理旧形状。

## 后果

- 头部格式本身也参与版本管理（`magic` + `schema_version`），未来若改头布局需要独立版本号。
- 拒绝降级：低版本程序读不了高版本文件时必须给出明确中文错误并提示升级，不能尝试部分加载。
- `kdf_version` 与 `schema_version` 是两套独立的单调计数器：前者随封套存储、按封套各自升级，后者升级重写整个正文。
- 头部整体在正文 AAD 覆盖范围内，因此重写封套（改主密码、KDF 升级、轮换恢复码）时正文密文须随新头部重算——条目明文不变，仅密文与认证标签重新生成，成本可忽略。
