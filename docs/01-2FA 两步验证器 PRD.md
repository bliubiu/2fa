## 1\. 产品概述

一款**完全离线、本地加密、开源可控**的 TOTP 两步验证命令行工具。它把用户全部账号的 2FA 密钥集中存放在一个本地加密保险库中，全程不联网、不上传、不统计。

对标 FreeOTP、Aegis，解决 FreeOTP 明文存储、无备份、无法迁移的问题。差异点在于：**加密等级高于 FreeOTP、迁移能力优于 Aegis（双轨加密备份）、且是纯粹的单文件工具，不引入数据库与前端供应链**。

## 2\. 产品定位

- **隐私优先**：全程离线，代码中不存在任何网络调用路径
- **本地加密**：所有密钥高强度加密存储，杜绝明文落盘
- **不丢数据**：强制恢复码 + 加密备份双保险
- **轻量可审计**：单一 Rust 工具链，纯库依赖无 C 代码

**明确不做**：云同步、账号体系、找回密码服务、多设备漫游。任何需要服务器的能力都会破坏「不上传任何数据」这一定位。

## 3\. 技术架构

### 3\.1 工程结构

Cargo workspace，两个 crate：

```
2fa/
├── Cargo.toml            # workspace
├── crates/
│   ├── 2fa-core/         # 库：零终端依赖、零环境感知
│   │   └── src/
│   │       ├── domain/       # 纯逻辑：TOTP/Base32/条目模型/otpauth 解析。完全不碰 IO
│   │       ├── vault/        # 存储：加密、序列化、原子写入、文件锁、内存保护
│   │       ├── usecase/      # 编排：初始化、解锁、条目 CRUD
│   │       ├── importexport/ # otpauth 文本、GA protobuf、明文导出序列化。纯数据处理，文件读写由调用方完成
│   │       └── qrcode/       # 接收调用方读入的图片字节，解码出二维码载荷字符串
│   └── 2fa-cli/          # 二进制：参数解析、路径解析、终端呈现、REPL
```

**边界约束（编译期可验证）**：`2fa-core` 不得依赖任何终端/UI 库，不得自行读取环境变量或当前工作目录。所有上下文（保险库路径、是否交互、时钟来源）由 `2fa-cli` 解析后作为参数传入。这条约束保证未来 Tauri 或任意前端可直接复用 core 而不改动它。

### 3\.2 依赖选型

全部选用纯 Rust 实现，**整个项目不引入任何 C/C++ 代码**，以此消除交叉编译与平台绑定的构建风险。

| 用途 | 选型 | 说明 |
|---|---|---|
| 对称加密 | `aes-gcm` | AES-256-GCM，支持 AAD |
| 密钥派生 | `argon2` | Argon2id |
| MAC | `hmac` + `sha1` / `sha2` | SHA1/SHA256/SHA512 |
| Base32 | `data-encoding` | RFC 4648 无填充变体 |
| 内存零化 | `zeroize` | volatile write + 内存屏障 |
| 序列化 | `serde` + `serde_json` | 保险库正文 |
| 随机数 | `rand_core` + `getrandom` | 密钥、盐、nonce 生成 |
| 二维码解码 | `rqrr` | 纯 Rust。排除 `zbar` / `zxing-cpp`（C/C++）与 `quirc-rs`（捆绑 C 代码） |
| 命令行 | `clap` | derive 模式 |
| 密码输入 | `rpassword` | 关闭终端回显 |
| 交互式行编辑 | `rustyline` | REPL |

**MSRV = 1.85**（`aes-gcm` 0.11 / `argon2` 0.6 / `zeroize` 1.9 的共同下限）。

**供应链要求**：`Cargo.lock` 必须提交；CI 必须跑 `cargo audit`；新增依赖需说明为何不能用已有依赖实现。

### 3\.3 保险库文件格式

单个文件，`vault.json`：

```
┌─ 明文头部 ─────────────────────────────┐
│ magic          "2FAVLT\0"（防误开）     │
│ schema_version  1                       │
│ 封套列表                                │
│   ├ 主密码封套：盐 + kdf_version + 密文  │
│   └ 恢复码封套：盐 + kdf_version + 密文  │
│ nonce          12B                      │
└──────────────────────────────────────┘
   ▲ 以上全部字节（含 magic）作为正文 GCM 的 AAD
   │ 任何篡改 → GCM 认证失败 → 文件被拒
   ▼
AES-256-GCM 密文
└ JSON 正文：{ schema_version, created_at, entries: [...] }
```

**明文头部只含密码学元数据**。条目内容、服务商名称、条目数量全部在密文内。攻击者拿到文件只能得知「这是个 2FA 保险库，使用了 AES-256-GCM，密钥派生成第 1 版」。

**每个封套 = salt(16B) + kdf_version + 密文**：封套密文以自身的盐与 `kdf_version` 作为 AAD，重写任一封套都不会使另一封套认证失败；头部整体（含 magic）又作为正文 GCM 的 AAD，构成双重防篡改。重写封套（改主密码、KDF 升级、轮换恢复码）时条目明文不变，正文密文随新头部重新生成。

**序列化用 JSON 而非 MessagePack**：OTP 条目的每个字段本来就是文本（密钥是 Base32 文本），紧凑编码收益接近零；而 JSON 的**可救援性**是决定性的——用户的密钥一旦全部锁死、备份文件损坏或需要跨大版本升级，JSON 能用任意语言写十行脚本抢救数据。

**原子写入**：临时文件 → fsync 文件 → rename 覆盖 → fsync 父目录。任何时刻断电都不会得到半截文件。

**进程锁**：`2fa-cli` 用 advisory file lock 独占保险库，防止 CLI 会话与另一个 CLI 进程并发写坏数据。锁被强杀后残留时，靠 PID + 起始时间戳校验判定失效并接管。

### 3\.4 密钥架构

一把随机生成的 32 字节**保险库密钥**是唯一能解密正文的东西，它被两个独立的**封套**分别加密：

```
保险库密钥（随机 32B，永不离开内存除非加密）
    ├── Argon2id(主密码, salt_主) → KEK_主 ──AES-256-GCM──→ 主密码封套
    └── Argon2id(恢复码, salt_恢) → KEK_恢 ──AES-256-GCM──→ 恢复码封套
                                                  ↓
                                    任一封套解开 → 保险库密钥 → 解密正文
```

- **改主密码只重写主密码封套**，保险库密钥与条目内容完全不动（条目明文不变，正文密文随新头部重算）
- **恢复码是单枚高熵随机串**，不是用户自选——否则会被弱口令字典攻破，等于没有第二把钥匙
- **恢复码用后轮换**：用恢复码成功恢复后必须生成新恢复码并重写恢复码封套，旧码作废
- **恢复码校验必须恒定时间**，避免时序侧信道泄露正确位数
- 每个封套自带专属的盐与 `kdf_version`，可独立升级、互不影响
- **无「找回密码」**：没有服务器，唯一的恢复路径是恢复码或用户自己保存的加密备份
- **首次设置必须强制**：打印恢复码与生成加密备份，用户未确认已保存则不允许进入主界面

### 3\.5 密钥派生参数

每个封套各持一份 `kdf_version`，代码内置版本→参数查表：

| kdf_version | 算法 | m (KiB) | t | p |
|---|---|---|---|---|
| 1 | Argon2id | 19456 | 2 | 1 |

**不使用直接存参数的写法**：文件里存的是不可调的版本号，攻击面更小，升级路径也更确定。

**自动升级**：解锁成功后，若某个封套的 `kdf_version` 低于当前版本，立即重写该封套，并按新头部重算正文密文（条目明文不变）。两封套版本可能短暂不一致（升级中途被打断），属正常中间态。

**参数不可被降级篡改**：每个封套的 `kdf_version` 同时被封套自身 AAD 与正文 GCM 的头部 AAD 覆盖，攻击者拿到文件后无法把版本改小以加速离线爆破——篡改会导致 GCM 认证失败。

### 3\.6 保险库路径解析

按优先级依次尝试：

1. `--vault <路径>` 显式指定
2. 当前工作目录下存在 `.2fa/vault.json` → 使用它
3. 平台惯例路径：
   - Windows：`%APPDATA%\2fa\vault.json`
   - macOS / Linux：`$XDG_DATA_HOME/2fa/vault.json`，未设置时回退 `~/.local/share/2fa/vault.json`

**硬性约束**：

- **每条命令都必须回显当前使用的保险库绝对路径**。用户会因为 `cd` 到别处而切换到项目内保险库，如果静默切换，用户会在错误的保险库上增删条目而毫无察觉。
- 首次在 CWD 创建 `.2fa/` 目录时必须显式提示「已在本目录创建项目保险库」。
- `2fa status` 子命令专门用于显示当前路径、来源（`--vault` / `项目内` / `平台惯例`）与条目数量。

### 3\.7 内存保护

- **零化必做**：所有密钥、封套派生值、明文密钥字段使用 `zeroize::Zeroizing<T>` 包装。这些类型**禁止 `Clone`**——一个 `#[derive(Clone)]` 会产生普通 `Drop` 清不掉的副本，且编译器不会报错。`serde` 序列化密钥字段时使用自定义实现，序列化后立即清零中间缓冲。
- **锁页与禁用 core dump 为尽力而为**：Unix 用 `mlockall(MCL_CURRENT | MCL_FUTURE)` + `setrlimit(RLIMIT_CORE, 0)`；Windows 用 `VirtualLock` + `SetErrorMode`。**失败时向 stderr 警告并继续**，不得因此拒绝服务——容器环境与受限 ulimit 下这些调用必然失败。
- 保险库密钥与条目明文按需驻留，条目操作完成后立即归零。

## 4\. 核心功能需求（MVP）

### 4\.1 验证码生成

- **TOTP**（RFC 6238）：SHA1 / SHA256 / SHA512 × 6 位 / 8 位 × 任意 period（默认 30 秒）
- **Steam Guard**：HMAC-SHA1，5 位，自定义字母表 `23456789BCDFGHJKMNPQRTVWXY`，30 秒
- **不支持 HOTP**，理由见[第 9 章](#9-已作废的初版要求)
- 验证码输出包含剩余秒数；REPL 的 `watch` 命令循环刷新倒计时

### 4\.2 otpauth URI 解析

- 解析 `otpauth://totp/<label>?secret=...&issuer=...&algorithm=...&digits=...&period=...`
- **issuer 冲突统一**：路径前缀（`otpauth://totp/GitHub:alice`）与 query 参数（`?issuer=GitHub`）不一致时，**以 query 为准**（Google Authenticator 的行为），并记录警告
- 密钥去除填充字符与空白，按需自动补齐 Base32 填充后再解码；宽容接受小写输入
- 未知参数不报错，忽略即可（真实世界的 URI 里充斥着各家自定义参数）

### 4\.3 二维码解析

- 读取本地图片文件（PNG / JPEG / GIF / WebP），提取 `otpauth://` 与 `otpauth-migration://`
- **这是项目唯一处理不可信外部输入的环节**，必须做输入校验：文件大小上限、像素数上限、解码失败给出明确中文错误
- 图片解码与二维码解析器纳入 fuzz 测试范围
- 摄像头实时扫码属 V1.1（需要 GUI）

### 4\.4 保险库操作

- 首次运行引导（`2fa init [--project]`，见第 4.6 节）：设置主密码 → 生成并打印恢复码 → 生成首份加密备份 → 强制确认已保存
- 解锁、改主密码、查看状态（路径/来源/条目数/派生版本——取两封套中较低者）
- 用恢复码恢复成功后强制轮换恢复码：生成新恢复码、重写恢复码封套、旧码作废
- 条目增删改查、按服务商与账号搜索、分组标签
- 空闲超时自动锁定（默认 5 分钟，可配置）

### 4\.5 导入导出

**导入**（三种，全部进入 MVP）：

1. `otpauth://` 纯文本批量导入，一行一条，忽略空行与 `#` 注释行
2. **Google Authenticator 迁移二维码**（`otpauth-migration://`）：base64 + protobuf，手写 varint 解析。导入后必须提示用户「立即删除 Google Authenticator 中的原始迁移数据」——该二维码里的密钥是明文，任何人拍屏即可取走
3. 自家加密备份文件（字节拷贝），导入前显式确认覆盖当前数据

**导出**：

1. **加密备份**（默认、安全）：保险库文件的字节级拷贝
2. **明文 otpauth 文本**（危险出口）：必须满足全部门槛——要求输入条目数或确认词二次确认、必须显式指定输出路径、文件首行写入中文警告注释、导出后立即提示用户删除

### 4\.6 CLI 交互

**主交互为 REPL**：`2fa` 无参数启动，输一次主密码进入会话。

```
2fa> list              列出全部条目与当前验证码
2fa> watch              循环刷新倒计时（Ctrl-C 退出）
2fa> add                交互式添加条目
2fa> show <id>          显示条目密钥（二次确认并提示为明文）
2fa> del <id>           删除条目
2fa> edit <id>          编辑条目
2fa> find <关键字>      搜索
2fa> import <文件>      导入（自动识别 otpauth 文本 / GA 迁移 / 加密备份）
2fa> export backup <文件>   加密备份（保险库文件字节拷贝）
2fa> export plain <文件>    明文导出（危险出口，四道门槛）
2fa> passwd             修改主密码
2fa> recover            交互式输入恢复码重新解锁，成功后强制轮换恢复码
2fa> lock               主动锁定
2fa> status             显示保险库路径、来源、条目数、派生版本
2fa> help               帮助
```

**单次命令模式**供脚本与管道使用：`2fa --stdin-password list` 形式，每条命令独立进程，执行完即擦除内存退出。初始化用 `2fa init [--project]`：默认在平台惯例路径创建保险库，`--project` 在当前目录创建 `.2fa/vault.json` 并显式提示。

**会话安全**：空闲超时自动锁定并归零内存；`lock` 命令立即锁定；进程退出时无条件归零。

### 4\.7 CLI 之外

GUI（桌面）与移动端 App 均为 **V1.1 及以后**。终局仍为跨端，但 MVP 只交付库与 CLI。

## 5\. 非功能需求

### 5\.1 安全要求

- 代码中不存在任何网络调用；不引入任何网络类依赖
- 全程离线，无统计、无遥测、无崩溃上报
- 禁止明文存储任何密钥；明文导出是唯一例外且必须走完全部门槛
- 内存中的密钥按第 3.7 节处理
- **日志绝对禁止记录**：密钥、保险库密钥、封套派生值、恢复码、主密码、加密前后的正文。脱敏规则中「密码」一项必须明确包含 OTP 密钥——这是初版规范里最危险的缺口
- 日志默认只输出到 stderr，不落盘；文件日志为 opt-in
- 所有错误信息使用中文，且不回显敏感输入

### 5\.2 性能要求

在 4 核桌面 CPU 参考机上：

| 指标 | 目标 |
|---|---|
| 冷启动到提示符 | < 100 ms |
| 主密码解锁（含 Argon2id） | < 500 ms |
| 1000 条目 `list` 渲染 | < 50 ms |
| 单条 TOTP 计算 | < 10 µs |
| 备份 5000 条目（约 550 KB） | < 200 ms |

### 5\.3 兼容性要求

- **完全通过 RFC 4226 与 RFC 6238 官方测试向量**（RFC 4226 Appendix D 共 8 组；RFC 6238 Appendix B 共 6 个时间点 × 3 算法，SHA256 用 32 字节 seed、SHA512 用 64 字节 seed）。这是「与所有平台 100% 一致」的唯一证明方式，不得以「看起来对」代替
- 随机源使用操作系统 CSPRNG，禁止任何形式的伪随机或退化实现
- 时间比较使用单调时钟校准的墙钟，验证码刷新无可见偏移

## 6\. 里程碑规划

版本号采用双轨制（详见 [`00-项目文档格式.md`](./00-项目文档格式.md)）：`Cargo.toml` 用 SemVer 0.x，CHANGELOG 与 Git Tag 用 CalVer `YYYY.MM.DD.MICRO`。下表的「里程碑名」不是版本号。

| 里程碑 | 内容 | 可用性判据 |
|---|---|---|
| **M1 算法内核** | domain 模块：Base32、HMAC、TOTP、Steam Guard、otpauth 解析 | RFC 官方向量全绿；Steam 与 Aegis/steamguard-cli 交叉验证一致 |
| **M2 保险库** | vault 模块：封套、KDF、格式、原子写入、锁、内存保护、迁移链 | 加条目→落盘→读回字节一致；篡改头部任一字节必被拒 |
| **M3 CLI 骨架** | init、参数解析、路径解析、REPL、单次命令、条目 CRUD、日志 | 20 条目 `list` + `watch` 可用；超时自动锁定生效 |
| **M4 导入导出** | otpauth 文本、GA 迁移二维码、加密备份、明文导出 | 往返无损；明文导出门槛全部生效 |
| **M5 二维码** | 图片解析、fuzz | 任意畸形图片不 panic、不挂死 |
| **M6 加固发布** | 文档、日志、供应链审计、跨平台验证、CHANGELOG | `cargo audit` 无高危；Windows/macOS/Linux 实机验证 |

## 7\. 开发清单

1. `domain/totp` —— TOTP 与 Steam Guard 计算、动态截断
2. `domain/base32` —— Base32 编解码（宽容解析）
3. `domain/otpauth` —— otpauth URI 解析与序列化
4. `domain/entry` —— 条目模型、分组、搜索
5. `vault/envelope` —— 封套读写、KDF 版本查表与自动升级
6. `vault/format` —— 明文头部、AAD 组装、JSON 正文、schema 迁移链
7. `vault/storage` —— 原子写入、文件锁、路径解析、内存保护
8. `usecase` —— 初始化、解锁、CRUD、导入导出编排
9. `importexport` —— otpauth 文本、GA protobuf、明文导出序列化
10. `cli` —— REPL、单次命令、参数与路径解析、终端呈现
11. `qrcode` —— 图片字节解码为二维码载荷字符串（`rqrr` + `image`，仅字节进出，不碰文件 IO）

## 8\. 日志规范要点

- **默认只输出到 stderr，不写文件**。文件日志为 opt-in（`--log-to-file`）
- 文件日志路径遵循平台数据目录约定（**不使用「项目根目录/logs/」**——CLI 是 PATH 上的二进制，没有项目根目录）
- 开启文件日志后保留期 **7 天**（非 32 天），并提供 `2fa logs purge`
- 日志级别 DEBUG / INFO / ERROR，由 `RUST_LOG` 或 flag 指定，默认 INFO
- 内容全中文，格式 `[YYYY-MM-DD HH:MM:SS.SSS] [级别] [进程ID] [模块:行号] - 内容`
- **第一条硬性规则是禁止记录密钥**，见第 5.1 节

## 9\. 已作废的初版要求

初版 PRD 存在 6 处自相矛盾或不可实现的表述，全部作废：

| 初版位置 | 原表述 | 作废理由 |
|---|---|---|
| §3.2 | 「不使用 SQLite/SQLCipher」 | 与 §8.8「几千条改用 rusqlite + SQLCipher」矛盾。已定永久使用单文件 JSON（`adr/0001`） |
| §3.2 | 「OTP 列表 MessagePack 序列化」 | 与可行性文档「JSON 作为内部结构」矛盾。已定 JSON，理由见 3.3 |
| §4.1 | 「支持 HOTP（兼容旧系统）」 | HOTP 是唯一有状态的时间步算法，每次使用后必须递增并持久化计数器。从备份恢复后计数器必然落后于服务端，**之后所有验证码全错且无法自愈**；多设备导入同一备份会导致永久错位。TOTP 是无状态纯函数，恢复后必然正确。Steam Guard 虽为私有变体但无状态且用户基数大，故收录 |
| §4.6 | 「命令行完全复用 Rust core，与 App 数据互通」 | 手机端物理不可行：iOS App 数据在沙箱容器内，Android 私有目录需 root，Keychain 条目仅限本 App access group。互通仅在桌面端成立。MVP 无 GUI，此条移至 V1.1 且需重新表述 |
| §6 | 「同时支持 CLI + 桌面 + 手机，全平台统一核心」 | 统一的是核心代码而非数据。手机端是数据孤岛。原表述暗示了跨端同步能力，属误导 |
| §7 | 「V1.0 MVP / V1.1 正式版」 | 与项目 CalVer 版本规范冲突。已改为里程碑命名（M1–M6） |
| §8.8 | 「未来改用 rusqlite + SQLCipher」 | 见 `adr/0001`。实测 5000 条目仅约 550 KB，解密 < 5 ms、计算 < 10 ms、搜索 < 1 ms，数据库解决的是不存在的问题，而 SQLCipher 带来 OpenSSL 五平台交叉编译与备份不再是字节拷贝两项真实成本 |
