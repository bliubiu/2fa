# 内存残留防护：零化必做，锁页与禁 core dump 尽力而为

密钥、封套派生值、明文密钥字段全部用 `zeroize::Zeroizing<T>` 包装并在离开作用域时归零。操作系统层面的保护（Unix `mlockall` + `setrlimit(RLIMIT_CORE, 0)`，Windows `VirtualLock` + `SetErrorMode`）为**尽力而为**：失败时向 stderr 警告并继续，不阻断功能。

## 为什么零化是必做而锁页不是

零化是纯用户态的，无条件可行，且不做就一定会泄露——`Drop` 里的一次普通写操作会被编译器优化掉，而 `zeroize` 用 `volatile write` 加内存屏障保证它不被优化。相比之下 `mlockall` 需要 `CAP_IPC_LOCK` 权限或足够的 `RLIMIT_MEMLOCK`：Docker 默认容器、无特权 CI runner、受限的 systemd 服务单元都会失败。

**把锁页失败当作拒绝服务是错误的取舍**：它会让产品在容器与受限环境下直接不可用，而真实的保护收益仅限于「防止本机其他进程读取本进程内存」这一较窄的攻击面。正确做法是能做到就做，做不到就明说，而不是因此不给用户验证码。

## 为什么锁页仍然要做

CLI 是短命进程且默认不写文件日志，REPL 会话可能持续数小时。在这两段时间里，密钥有充分机会被换出到 swap 或 pagefile。`setrlimit(RLIMIT_CORE, 0)` 成本为零且无权限要求，没有理由不做；`VirtualLock` 在 Windows 上桌面应用通常已具备权限。

## Rust 特有的陷阱

`#[derive(Clone)]` 会产生密钥副本，而普通 `Drop` 只清理原始那一个。编译器不会对此发出任何警告。因此**密钥类型必须禁止 `Clone` 与 `Copy`**，并让 `Debug` 实现固定输出 `«已隐藏»`，使其在任何日志级别下都无法被格式化打印。

## 后果

- 解锁耗时实测（`2fa bench`）必须写入 PRD 第 5.2 节性能报告；若在受限环境下锁定失败，报告需注明此时密钥可能被换出。
- 长时间运行的 REPL 会话在锁定失败时的风险高于短命单次命令，README 需提示用户不要在共享机器上保持会话。
