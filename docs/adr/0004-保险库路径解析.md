# 保险库路径：CWD 下 `.2fa/` 优先于平台惯例路径

路径解析优先级为 `--vault <路径>` > 当前工作目录下的 `.2fa/vault.json` > 平台惯例路径（Windows `%APPDATA%\2fa\vault.json`，macOS/Linux `$XDG_DATA_HOME/2fa/vault.json` 或 `~/.local/share/2fa/vault.json`）。

## 为什么不是纯平台惯例路径

2FA 密钥在语义上是全局的——你的 GitHub 2FA 与你在哪个目录下工作无关。但项目内保险库有三个实际好处：保险库与项目一起进版本控制忽略名单或备份策略、多个身份可以并存（例如工作与私人各一份）、不会因为换机器后找不到配置目录而困惑。用户明确选择了这个便利性，代价是接受「我到底在用哪一份保险库」这个需要产品来兜住的认知负担。

## 为什么不能只靠 CWD

完全不依赖 CWD 会让自包含的好处消失；完全依赖 CWD 则更糟——`2fa` 从 cron、IDE 任务、任意 PATH 位置启动时行为不确定，且在 A 项目里看到工作密钥、在 B 项目里看到私人密钥时，用户极难察觉。因此定为**默认全局、项目内优先**的折中：项目内的保险库是显式选择的结果（需要事先存在 `.2fa/` 目录，而首次创建时会有明确提示），不会凭空出现。

## 后果

- **每条命令必须回显当前保险库绝对路径与来源标记**（`--vault` / `项目内` / `平台惯例`）。这一条是硬性约束，删掉它就等于允许用户在一个错误的保险库上增删条目而毫无察觉。
- 首次在 CWD 创建 `.2fa/` 目录时必须显式提示「已在本目录创建项目保险库」，不能让用户以为只是普通副作用。
- `2fa status` 专门用于显示路径、来源、条目数与 `kdf_version`。
- README 与首次设置引导必须解释清楚存在多份保险库的可能，否则这是最可能收到 bug 报告的来源。
